A filter like `object_type = cyclist` finds a rider waiting at the curb just as easily as one cutting across our lane. If I had a reliable label for the crossing itself, I’d use it. With a presence label, I need to search what’s happening in the video.

Say a cyclist crosses in the first few seconds and our car brakes for a red light toward the end. I’d waste a review slot if that clip came back for a crossing while our car was slowing.

## Choose the unit of search

I’d use a whole-clip embedding to find footage near a junction. For a crossing, I cut the clip into shorter windows so the encoder has less unrelated footage to summarize and I know which stretch of the speed trace to check.

I start a six-second window every four seconds. In a 20-second clip, the last window starts at 16 seconds and runs to the end. Overlapping by two seconds gives an event near a cut a better chance of appearing in one piece. It also means more vectors to store and more hits from the same clip.

For each window, I sample eight frames and encode them together as one 256-dimensional vector. The model maps the text query into that same vector space so I can rank the windows by similarity. I calculate the motion field separately. I take the last valid speed sample in the window, subtract the first, and divide by the time between them.

## Keep conditions at the same granularity

I search for “Cyclists ride across the road ahead at a junction” and use a motion filter of ≤ −0.5 m/s² on our car’s net speed-change rate.

In the red-light example, the two events happen in different parts of the clip. The crossing might rank well in the 0–6 second window, and the 12–18 second window might pass the speed filter. The search needs to check the speed on the same window it ranks. Otherwise the red-light stop can count as braking during the crossing.

Six seconds is still a fairly wide interval. To see whether we started braking before the cyclist entered the lane, I’d line up the video with the timestamped speed trace.

## Model the clip and its windows

One option is a row per window and a separate record for the source clip. That’s handy if I need to re-embed or delete windows one at a time. The application follows the clip ID to find the video and coordinates updates that affect both records. To search for crossings in a particular city, I could first find the clip IDs for that city, then search only their windows.

In my local Milvus 3.0.2 setup, I had a bounded set of windows that I managed with the clip. I kept them in one entity per clip, in a StructArray called `observations`. Each element holds the vector, timestamps, and motion fields for one interval.

I search `observations[window_vector]` and use `element_filter` to check the motion fields on each window before it can participate in the search.

```text
element_filter(
  observations,
  $[motion_available] == true
  and $[net_speed_change_mps2] <= -0.5
)
```

The video can live in object storage with either layout. The app still has to resolve the media reference and seek to the matched offset.

For these three clips I used labels and telemetry to find candidates. I’d want the same view for vector search results, with the clip ID and matched time range together. I can send that pair to a teammate, and they can jump to the same moment or scrub back to see the approach.

Two overlapping windows can both catch the same crossing. When review time is tight, I’d group by clip ID and show the best window from each recording. I’d keep individual hits when the job is to find several events in one drive. Grouping by clip ID still leaves me to check whether two clips show the same encounter.

## Decide what to review next

If I’m investigating riders who emerge from behind parked cars, I’d keep some clear crossings for comparison and search for those occluded approaches next. If I keep finding the same few encounters, I’d ask the collection team for more routes with cars parked close to crossings.

For the search workflow, I’d track how long it takes to get a shortlist and how many distinct encounters survive review. To measure retrieval quality, I’d use queries with human judgments on which clips match. To check whether the vehicle handles the crossings better, I’d run a separate test on encounters held out from training.
